# Workforce V1.2 – Unified Runtime Foundation

The current Registry, advanced specialist, custom-agent and Manager/QA handlers retain their existing execution and authorization paths. A shared post-execution journal assigns each returned task a server-generated task UUID and run UUID, with the canonical employee identity. The original browser task ID, task result and approval state remain unchanged.

In production, the journal inserts metadata into existing Supabase jarvis_tasks (type workforce-agent-execution) and jarvis_agent_runs tables, verifies returned IDs, and links manager-delegated children to the parent runtime task. Existing Cloudflare queue and Jarvis Redis job scheduling are untouched. No job is queued by this journal. A local/autonomous Nova execution is identified by the existing trusted server-side symbol, not a request parameter.

Only normalized statuses, agent/provider/model identifiers, timestamps, duration and hashed legacy/source references are persisted. Raw prompts, customer details, product payloads, generated content and error bodies are excluded. Cost remains unknown rather than inferred. A completed journal row means an execution returned, not that the product or listing was approved.

Both writes must be confirmed before the response reports recorded. A partial or unconfirmed journal is exposed without repeating the actual agent/model call. Test and preview environments do not write the journal. The Registry and all four compatibility execution handlers now attempt to insert a running task before dispatching an existing handler, then updates that same row and records its run. Exceptions after a confirmed claim are recorded as failed attempts. If the worker disappears before returning, the history marks the still-running row as interrupted/unconfirmed after 15 minutes, without modifying it or re-executing the request.

Authenticated GET /api/ai-agent-run-registry?view=runtime&limit=30 exposes bounded sanitized history; the existing JARVIS System status also shows recent entries. No new execution API route or subscription; the read-only storage RPC uses a migration. Production journal writes and readback still require live acceptance. The Task Center now uses the shared durable task store for new manual drafts and explicitly approved local margin jobs. Historical local drafts are not automatically migrated or replayed.

## Registry idempotency boundary

Authenticated Registry callers may provide an opaque Idempotency-Key header (16–128 ASCII letters, digits, underscores or hyphens). A deterministic UUID is derived from the key and claimed by inserting into the existing jarvis_tasks primary key before any model call. The raw key is not stored. Concurrent or later calls with the same key receive HTTP 409 and the existing task ID; no output is replayed. An uncertain claim that cannot be confirmed returns HTTP 503, without dispatching a model. The same key remains reserved while its task row exists; a new key represents a new explicitly requested execution. Older unkeyed requests retain their previous availability behavior if the database is unavailable. The autonomous Nova cost restrictions and external action locks are unchanged. This does not guarantee exactly-once execution for unkeyed requests or across independent new request keys, and does not yet provide automatic resumption or durable input payloads. Production claims have not been exercised against the actual database.


## Storage budget and retention inventory

The existing six-hour Infrastructure Health Monitor additionally calls the service-role-only, SECURITY INVOKER, read-only RPC jarvis_workforce_storage_health. Apply migration 20261128010000_jarvis_workforce_storage_health.sql before expecting a confirmed measurement. The RPC returns PostgreSQL database bytes, task/run table bytes and the number of terminal Workforce execution records older than 90 days. It exposes no records or identifiers and grants execution only to service_role. The 500,000,000-byte operational budget is a conservative Free-plan reference, not the Supabase billing usage meter. Warn at 70% (350 MB) and mark critical at 85% (425 MB). Missing or stale measurements are unverified.

The retention policy is inventory-only: no deletion, compaction, archive transfer or automatic plan upgrade. It excludes running and queued jobs, other task types and memory tables. Before any removal, design a verified export, preserve manager-child relationships and durable idempotency tombstones, and obtain explicit approval. Never delete keyed task rows just because they passed the retention age, since they currently enforce duplicate protection. NAS export is a later optional step, not implemented.

At four scheduled cycles per day, this adds one aggregate database request per cycle (about 120 in a 30-day month); no new cron, provider, Redis command or subscription. Actual performance and database size are workload-dependent. The database currently measures 12,569,747 bytes in a read-only SQL check; that is a snapshot, not a hardcoded runtime value.


## Browser compatibility and controlled retry

All four existing direct handlers share the same lifecycle boundary; nested Registry and Manager delegations do not create duplicate claims. The existing advanced settings fetch bridge adds opaque keys to same-origin JSON POSTs for known execution endpoints, preserves supplied keys and settings, and rejects concurrent aliases of the same employee within the page. It does not affect other endpoints, reads, or cross-origin requests. The legacy retry button now requires a recorded failed execution and explicitly confirms a new analysis with current settings and matching selected source ID. The server validates the failed task and failed run, same canonical agent, manual/registry origin, and maximum depth of two. A deterministic successor UUID enforces at most one successor per failed attempt, independent of competing request keys. Running, unconfirmed, Manager, delegated and Nova worker attempts cannot use this manual retry mechanism. Raw inputs are not persisted or reconstructed: this is a new explicitly requested analysis, not automatic replay. The existing browser task-center form now creates authenticated server-backed manual drafts with encrypted title and prompt. No legacy draft is automatically executed. No queue replacement or automatic reprocessing is introduced.


## Durable task inbox and first bounded automation

The authenticated registry view=queue supports create, cancel and create_auto_margin operations. Manual drafts are encrypted using AES-256-GCM with an HKDF-derived domain-specific key from the server-only Supabase service-role credential. Key rotation requires a planned migration of pending drafts. The original draft is claimed with a conditional queued-to-running update and title/prompt/employee/priority validation; its prompt is discarded at claim time. The Task Center reads at most 50 server rows and uses the existing composer for manual starts. Local historical records remain local. Server reads are event driven, not polled. Manual drafts do not automatically run, and historical inputs are not reconstructed.

The new explicitly confirmed automatic margin task accepts exactly eight numeric cost/price fields with bounded ranges. The existing calculateProfitAnalysis engine runs directly without any model router, prompt, external API call or business-data write. It stores only the numerical result and status, removes input values at claim, and never grants listing approval. A conditional update of the shared jarvis_tasks row is the exclusive claim; cancelled and running jobs cannot be replayed by the cron. The existing authorized Vercel cron processes at most one such job in an idle Nova cycle, only when the original persisted JARVIS mode is autopilot (not the assisted-to-E5 promotion), the normal budget/guard decision allows execution, and local is permitted. The existing slot reservation and outcome accounting remain in force. The worker never expands its Nova pipeline scope or invokes Company OS for these margin jobs. Concurrent claims can consume a reserved slot without execution; no model cost is incurred. A failed or interrupted claim is not automatically retried. Old Redis/Cloudflare workers keep their existing scopes; full arbitrary background-agent execution and queue-engine consolidation are not part of this stage.

At most one additional bounded Supabase queue read per eligible idle five-minute cycle (~8,640/month at continuous eligibility); additional DB writes and existing Redis slot/metering operations only when a job is claimed or attempted. No new cron, subscription, queue provider or model calls. Actual usage and production acceptance remain to be verified. No migration or production task is created by the code changes alone. The storage RPC migration is still pending application.
