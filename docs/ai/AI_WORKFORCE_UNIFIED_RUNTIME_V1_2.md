# Workforce V1.2 – Unified Runtime Foundation

The current Registry, advanced specialist, custom-agent and Manager/QA handlers retain their existing execution and authorization paths. A shared post-execution journal assigns each returned task a server-generated task UUID and run UUID, with the canonical employee identity. The original browser task ID, task result and approval state remain unchanged.

In production, the journal inserts metadata into existing Supabase jarvis_tasks (type workforce-agent-execution) and jarvis_agent_runs tables, verifies returned IDs, and links manager-delegated children to the parent runtime task. Existing Cloudflare queue and Jarvis Redis job scheduling are untouched. No job is queued by this journal. A local/autonomous Nova execution is identified by the existing trusted server-side symbol, not a request parameter.

Only normalized statuses, agent/provider/model identifiers, timestamps, duration and hashed legacy/source references are persisted. Raw prompts, customer details, product payloads, generated content and error bodies are excluded. Cost remains unknown rather than inferred. A completed journal row means an execution returned, not that the product or listing was approved.

Both writes must be confirmed before the response reports recorded. A partial or unconfirmed journal is exposed without repeating the actual agent/model call. Test and preview environments do not write the journal. Direct legacy handlers still journal completed returned tasks only. The Registry now attempts to insert a running task before dispatching an existing handler, then updates that same row and records its run. Exceptions after a confirmed claim are recorded as failed attempts. If the worker disappears before returning, the history marks the still-running row as interrupted/unconfirmed after 15 minutes, without modifying it or re-executing the request.

Authenticated GET /api/ai-agent-run-registry?view=runtime&limit=30 exposes bounded sanitized history; the existing JARVIS System status also shows recent entries. No new API route, subscription or schema migration. Production journal writes and readback still require live acceptance. The next phase must connect all browser callers to the idempotent execution boundary, unify the remaining legacy tasks and introduce explicit controlled retries before automatic multi-agent execution is expanded.

## Registry idempotency boundary

Authenticated Registry callers may provide an opaque Idempotency-Key header (16–128 ASCII letters, digits, underscores or hyphens). A deterministic UUID is derived from the key and claimed by inserting into the existing jarvis_tasks primary key before any model call. The raw key is not stored. Concurrent or later calls with the same key receive HTTP 409 and the existing task ID; no output is replayed. An uncertain claim that cannot be confirmed returns HTTP 503, without dispatching a model. The same key remains reserved while its task row exists; a new key represents a new explicitly requested execution. Older unkeyed requests retain their previous availability behavior if the database is unavailable. The autonomous Nova cost restrictions and external action locks are unchanged. This does not guarantee exactly-once execution for legacy direct routes or unkeyed requests, and does not yet provide automatic resumption or durable input payloads. Production claims have not been exercised against the actual database.
