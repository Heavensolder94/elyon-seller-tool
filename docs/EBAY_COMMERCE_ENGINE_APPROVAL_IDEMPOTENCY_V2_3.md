## Simulation-only binding and ledger
lib/commerce-approval-v2-3.js creates immutable privately branded fixture bindings, requiring fixture: IDs, explicit simulated scope, target IDs as strings, marketplace/environment/account match, inventory origin, ACTIVE, EUR, timestamps, supplier quantity/availability, economics PASS fixture, product/state revisions, and no stock increases. Current and proposed price/quantity normalized; unchanged fields null. All targets sorted, operation key uses account/environment/marketplace/action, exact expected state including stateRevision and normalized changes (not review ID, time, actor, or row order). Binding additionally includes actor/workspace, target/content/evidence fingerprints, product and rule revisions. No raw secrets or product images. Listing/offer/SKU target keys account-scoped; listing lock conservatively covers all variants. Multiple variants in the same batch may share listing lock, duplicate offer/SKU prohibited. New changed expected state can produce a distinct operation; earlier same operation remains recorded. All fixture inputs are test evidence only, never actual evidence.
lib/commerce-simulation-ledger.js uses an injected Redis command, isolated random UUID namespace and simulation-only keyspace, one hash per account/environment/marketplace/action. All records (a: review, o: operation, i: operation hash, t: target hash) in one key; one EVAL per action, reads and checks first, one HSET for each mutation (including approval consumption, operation, idempotency and all locks). No separate multi-database lock or fallback. Redis TIME for expiry and freshness (24h, future rejected). Confirmation requires exact scope, revision, binding and fresh evidence; changed binding supersedes, revocation/expiry terminal, duplicate/overlap deny. Reservations require CONFIRMED and consume exactly once. Audit events attached per record, capped 24 with truncation marker; no claim of tamper-proof log. Denials for authorized record logged; scope mismatch returns generic not found. Hash capped 4000 fields, request <=128 KiB and batch <=50, fail closed on capacity, no TTL that can remove unresolved operations. No background cleanup; disposable test service destroyed after run. Future production retention must separately design archiving/pruning for old terminal reviews/operations and safe tombstone retention; current bound intentionally halts instead of silently deleting evidence. Persistent simulation data across adapter instances, no production storage adapter wired or allowed. REST adapter shape matches existing EVAL command convention; actual Upstash EVAL, consistency, durability, eviction/backup and retention are unverified. No production Redis write/test.
Approval states AWAITING_CONFIRMATION, CONFIRMED, EXPIRED, REVOKED, SUPERSEDED, CONSUMED; blocked production descriptor EVIDENCE_REQUIRED. Operation states RESERVED, PREPARED, EXECUTION_BLOCKED, SIMULATED, UNKNOWN_OUTCOME, RECONCILIATION_REQUIRED, RESOLVED, CANCELLED. Only allowed transitions; no execution state. External reference/result null. Release locks atomically only for definite no-execution cancellation or simulator resolution; unknown/reconciliation-required never release, no automatic retry. Lost reservation response returns ledger_unavailable_outcome_unknown; recover via persisted approval/operation reference, not another automatic write. Revision conflict checked, actor cannot read others' operation. Audit uses Redis clock; no access tokens. No actual reconciliation action until V2.4.

## Verification and merge order
Unit tests distinguish shared access vs verified scope, fixture binding, normalized keys, manipulations and adapter error; real Redis workflow tests races, overlap, revisions, expiration, cancellation, unknown outcome, lost response and persistent recovery. Default npm test skips the six real Redis test groups unless explicit isolated GitHub service container is provided. No claim of actual Redis until workflow success; Redis 7 test is not deployed Upstash verification. Company OS revision test checks stable/changed fingerprints. Company OS first (optional additive metadata, Seller fails closed even without it), then Seller Tool after CI/preview and explicit merge approval. V2.4 must not activate adapters until individual authenticated identity/workspace/eBay account, fresh offer/supplier evidence, canonical revision revalidation, live Redis guarantees and safe retention/archival are verified; add independent transport/reconciliation boundary, no automatic retry. V2.3 remains simulation-only and live flags false.
